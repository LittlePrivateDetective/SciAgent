# 本地模型部署 vs 云端模型部署

> 结论先说：**演示和小团队用云端，长期高频和数据敏感用本地，两者不是替代关系而是分工关系。**
> 本项目两条路都留着（`llm_route = auto / cloud / local`），控制台里可以直接切换与自测。

## 一、一张表看区别

| 维度 | 云端 API | 本地部署 |
| --- | --- | --- |
| 成本形态 | 按 token 付，用多少算多少；闲时不花钱 | 一次性买卡/租卡，闲时也在烧电、占机器 |
| 首字延迟 | 通常 0.6–2 秒（网络 + 排队） | 0.3–1 秒（无网络，但受显存带宽限制） |
| 吞吐 | 随时可扩，单 key 有并发上限 | 受显存与并发数约束，加卡才能扩 |
| 模型能力 | 能用上最强的那一档 | 同价位只能跑到 7B–32B 量级（量化后更低） |
| 上下文长度 | 128K 起，随意 | 受显存限制，长上下文要 PagedAttention 才撑得住 |
| 数据出域 | 论文原文会离开本机 | 全程不出内网 |
| 运维 | 供应商负责 | 你负责驱动、CUDA、显存、进程守护、升级 |
| 版本稳定性 | 供应商随时换版本，行为可能变 | 版本锁死，可复现 |
| 故障面 | 网络抖动、限流、区域故障 | 断电、OOM、驱动崩、单点无冗余 |
| 合规 | 需过数据出境/第三方评估 | 天然满足"数据不出门" |

## 二、本地部署的难点（按踩坑概率排序）

**1. 显存是第一约束，不是算力。**
7B 模型 fp16 约 14GB 权重，加上 KV cache，24GB 卡只够 1–2 路并发；
4bit 量化能压到 4–5GB，但中文长文理解和数值推理会明显退化——而科研问答恰恰吃这两项。
本项目语料 37 篇 / 19766 段 / 634 万字，检索阶段还好，**生成阶段**才是显存瓶颈。

**2. 吞吐与并发是乘法关系，不是加法。**
本地一台机器跑 7B，单路约 30–60 tok/s；3 路并发就掉到 15–25 tok/s。
本项目翻译一页正文（约 2500 字符）在云端 `qwen-flash` 下实测 120 tok/s、5–8 秒完成；
换成单卡本地 7B，同一页要 20–40 秒，"边滚边读"的体验就没了。

**3. 长上下文要靠推理框架，不是靠换模型。**
原生 transformers 跑 32K 上下文，KV cache 会把显存吃穿。要上 vLLM / SGLang 的
PagedAttention + 连续批处理，才能把 32K 上下文和多并发同时撑住——这时候"部署"已经
不是 `pip install` 的事了，是运维工程。

**4. 一个模型干不了所有活。**
本项目实际是四类调用：主对话（要推理）、逐段翻译（要吞吐、不能带思维链）、
写作（要长输出）、OCR（要视觉）。本地要么部署 3–4 个模型抢同一张卡，要么接受
"用非推理模型硬扛对话"，质量会掉一档。

**5. 量化是隐性质量损失。**
int8 基本无损，int4 在中文长句、数字、公式上会开始编——而科研场景最怕数字编错。
本项目所有数字都要过"溯源校验"，本地量化模型的幻觉率上升会直接顶到校验阈值。

## 三、云端部署的难点

**1. 账单不可预测。** 一次"整篇翻译"可能几百次调用；`top_k` 从 8 调到 20、
证据块从 4 调到 8，token 消耗近似翻倍。没有配额与预算护栏，很容易在演示当天超限。

**2. 限流与超时是最常见的"假故障"。** 并发 3 路以上很容易撞 429；
本项目为此加了重试 + 退避（`llm.py` 里 3 次重试），翻译并发默认 3 而不是更高。

**3. 版本漂移。** 同一个模型名，供应商换后端版本后行为可能变——尤其是"带思维链"的
模型，输出预算被推理过程吃掉、返回空串，本项目踩过两次（翻译、写作各一次），
最后靠"场景模型单独指定非推理模型"绕开。

**4. 数据出域。** 论文原文、未发表的想法、实验数据都会上传。学校/企业内网通常
不允许，这一条往往不是技术选择而是合规选择。

**5. 供应商锁定。** 不同家的 JSON 模式、函数调用、思维链字段都不一样。
本项目只依赖 OpenAI 兼容协议，换供应商改 `base_url + model` 即可，这层抽象必须做。

## 四、本项目的实测数据

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 云端主模型一次问答 | 1.2–2.2 秒 / 25–200 token 输出 | 控制台「连通性自测」实测 |
| 云端翻译吞吐 | 120 tok/s（qwen-flash） | 对比 qwen-plus 的 43 tok/s |
| 一页正文翻译 | 5–8 秒（云端，3 路并发） | 1157 字符选区 → 374 字译文 |
| 整篇中文论文译英 | 3.8 秒 / 1852 字符 | 1 页样本，3 路并发 |
| 语料规模 | 37 篇 / 19766 段 / 634 万字 | 当前演示库 |
| 数据库体积 | 95 MB | SQLite 单文件 |

按这些数字推算：如果本地用单张 24GB 卡 + 7B-int8，对话质量会低于当前云端模型，
翻译吞吐约为云端的 1/3–1/2，且无法同时跑视觉 OCR——**能跑通，但演示观感会明显下降**。

## 五、怎么选（决策矩阵）

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| 答辩 / 评审 / 对外演示 | 云端 | 质量与延迟都在最佳状态，网络问题用"模拟模式"兜底 |
| 学校/医院内网、涉密数据 | 本地 | 数据不出门是硬要求，质量可以靠流程补（人工复核） |
| 高频批量处理（几千篇） | 本地 | 边际成本趋零，可离线排队跑 |
| 低频、突发、模型要最新 | 云端 | 不为峰值买卡 |
| 混合 | **路由 + 降级** | 日常云端，断网/限流自动切本地，界面上如实标注走的是哪条 |

## 六、如果要把本项目本地化，落地顺序

1. **推理框架**：vLLM（OpenAI 兼容）起 7B–14B 模型，`llm_base_url` 指向
   `http://127.0.0.1:8000/v1`，`.env` 里 `LLM_ROUTE=local` 或控制台切"路由策略"。
2. **嵌入模型**：`bge-m3` 本地跑（`emb_provider=local`），避免检索也依赖外网；
   注意 `emb_dim` 要与模型一致，改完要**重建索引**。
3. **压测**：并发 1/2/4 三档，记录 P50/P95 首 token 延迟与 tok/s，再决定
   `trans_workers` 与 `rerank_top_n`。
4. **兜底**：保留云端 key，`llm_route=auto` + 失败重试 2 次后降级到本地，
   前端在回答里标注"本次由本地模型生成"。
5. **质量回归**：用 `tests/qa_suite.py` 全量跑一遍——重点看**数字溯源**与**引用命中率**，
   本地量化模型最容易在这两项掉分。

## 七、控制台里对应的开关

- 「云端模型」组：`llm_base_url` / `llm_model` / `llm_api_key` / `llm_temperature` / `llm_timeout` / `llm_route`
- 「本地模型」组：`ollama_enabled` / `ollama_base_url` / `ollama_model`
- 「检索与索引」组：`emb_provider` / `emb_model` / `emb_dim` / `vector_backend`（均标"需重建索引"）
- 概览页会实时显示：当前路由（cloud / local / mock）、本地 Ollama 是否可连通与延迟

切换顺序建议：先改地址与模型名 → 点「连通性自测」确认能通 → 再切路由 →
最后跑一次问答与翻译验证端到端。
