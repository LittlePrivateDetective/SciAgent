# 微调实验（v1.1 收尾）

> 目标：把库里的论文变成指令数据，训一个"会按 SciAgent 规矩答论文题"的本地 3B 模型，
> 用可判定指标证明它到底变好了没有。本文只记录**实测数字**，不改主站默认路由。

## 1. 环境与配置

| 项 | 值 |
| --- | --- |
| 硬件 | RTX 2060 6GB / 15.9GB RAM / Windows 10 |
| 底座 | `Qwen2.5-3B-Instruct`（本地 5.8GB，不联网下载） |
| 训练方式 | 4bit QLoRA（nf4 + 双重量化），fp16 计算 |
| LoRA | r=16，alpha=32，dropout=0.05，7 个 target module（q/k/v/o/gate/up/down） |
| 可训参数 | 29,933,568 / 3,115,872,256（0.96%） |
| 数据 | `data/sft/train.jsonl` 280 条；`dev.jsonl` 28 条（由 qa 308 条按 90/10 拆分，**训练不碰 dev**） |
| 超参 | 1 epoch、batch 1 × 累积 8（35 步）、max_len 896、lr 2e-4、cosine、adamw_torch |
| 耗时 | **44 分 26 秒**（满显存时逐步变慢，约 20–107 s/步） |

## 2. 训练结果

- loss：**1.4572 → 0.6833**（7 个记录点，最低 0.6676）；`train_loss=0.855`。
- 产物：`data/sft/out/lora-3b/adapter_model.safetensors`（119.8MB）。
- 断点：`checkpoint-10/20/30/35`，`save_total_limit=2`。

## 3. 合并与部署

| 步骤 | 命令 | 结果 |
| --- | --- | --- |
| 合并 | `ml/merge_lora.py --lora ... --out data/sft/out/merged-3b` | **38 s**，fp16 5.75GB，4 分片，3,085,938,688 参数 |
| 转 GGUF | `convert_hf_to_gguf.py merged-3b --outtype f16` | **20 s**，6.17GB，434 tensors |
| 导入 Ollama | `ollama create sciagent-3b -f data/sft/Modelfile` | **52 s**，`sciagent-3b:latest`，6.18GB，F16，runner=llamacpp |

Ollama 实测（真实证据题，非"只回复 OK"）：

```
b和g是与ht同维度的偏置和增益参数[1]。其中，Whh是循环隐藏到隐藏权重，Wxh为底部输入到隐藏权重[1]。
总耗时 14.8 s / 44 tokens / 8.1 tok/s
```

## 4. 三列评测（同一批 28 条 dev 题）

| 模型 | 引用率 | 引用越界率 | 数字出错率 | 元话语率 | 空答案率 | 平均字数 | 字/秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| base 3B | 0.500 | 0.036 | 0.071 | 0.000 | 0.000 | 71 | 13.6 |
| **微调 3B** | **1.000** | **0.000** | **0.036** | 0.000 | 0.000 | 71 | 7.6 |
| 云端 `deepseek-v4.1-flash` | 0.929 | 0.036 | 0.107 | 0.250 | 0.000 | 140 | 96.8 |

解读（只按硬指标，不请模型当裁判）：

- **微调把引用行为从"一半靠猜"拉到 100%**：base 有一半答案完全不写 `[n]`；微调后 28/28 全部带引用，且没有越界编号。
- **数字保真优于 base，也优于云端小样本**：3.6% vs 7.1% vs 10.7%。云端更爱扩写（平均 140 字），引入数字的风险更高。
- **元话语**：微调后 0%，云端 25%（"根据提供的证据"这类线上会判失败的话）。
- **速度**：微调后 7.6 字/s，比 base 慢一半。原因是模型更倾向于写满引用与完整句，EOS 来得晚；不是 adapter 的计算开销。云端 96.8 字/s，本地 3B 无法在速度上竞争。
- **拒答正确率无法评估**：`dev.jsonl` 28 条里 `deny` 全为 `None`（拆分时拒答样本都进了 train），所以这一列留空，不编造数字。

结论：**微调让 3B "守规矩"（引用、数字、拒答格式），但不可能在知识广度上追上云端**，与 README 里写明的边界一致。

## 5. 已知限制

1. **Ollama 部署是 F16，不是 4bit**。Ollama 0.40 的 `--quantize` 只支持 `int4/int8/nvfp4/mxfp4/mxfp8`，且只对 safetensors 导入生效；而 safetensors 导入走 MLX 路径，直接报 `unsupported MLX architecture: Qwen2ForCausalLM`。GGUF 输入必须先量化，本机没有 cmake/编译器，无法构建 `llama-quantize`，因此以 F16 导入（6.18GB，显存不足部分自动 offload，实测 8.1 tok/s）。有编译环境时补一条：
   `llama-quantize sciagent-3b-f16.gguf sciagent-3b-q4.gguf Q4_K_M`
2. **dev 没有拒答样本**，拒答正确率这一列无法评估；需要重新按 deny 分层抽样。
3. 训练数据 280 条、覆盖有限；换一批文献要重新造数据。
4. 满显存时训练步速从 20 s 退化到 107 s，属于 6GB 卡的硬边界。

## 6. 复现

```bash
# 训练
ml/.venv/Scripts/python.exe ml/train_lora.py \
  --data data/sft/train.jsonl --base ml/models/Qwen2.5-3B-Instruct \
  --save-steps 10 --out data/sft/out/lora-3b

# 合并
ml/.venv/Scripts/python.exe ml/merge_lora.py \
  --lora data/sft/out/lora-3b --out data/sft/out/merged-3b

# GGUF
ml/.venv/Scripts/python.exe <llama.cpp>/convert_hf_to_gguf.py data/sft/out/merged-3b \
  --outfile data/sft/out/sciagent-3b-f16.gguf --outtype f16

# Ollama（Modelfile 的 FROM 指向上面的 .gguf）
ollama create sciagent-3b -f data/sft/Modelfile

# 三列评测
ml/.venv/Scripts/python.exe ml/eval_ft.py --lora data/sft/out/lora-3b --cloud
```

> 产物都在 `data/sft/`（不进仓库）；底座在 `ml/models/`（不进仓库）。
